# Habloom 要件定義

最終更新: 2026-11-25

この文書は、Habloom の開発を始める前に合意した要件と技術構成をまとめたものです。実装を進める中で判断が変わった場合は、この文書を更新します。

## 1. 目的と対象ユーザー

### 目的

- 開発者本人が毎日使い、自分の習慣を続けられるようにする。
- Rust、Swift、Kotlin を初めて学ぶ題材とする。動くものを作るだけでなく、各言語の特性を理解しながら進める。

### 対象ユーザー

- 最初は開発者本人だけが使う。
- 手応えがあれば、後からストアで一般公開する。公開を妨げない設計にしておくが、公開に必要な対応(審査対応、プライバシーポリシーなど)は MVP に含めない。

### 対象プラットフォーム

| プラットフォーム | 位置づけ | 対応バージョン |
|---|---|---|
| iOS | 最初にリリースする | iOS 26 以上 |
| Android | iOS の後に対応する | 未決定 |
| Web | 対象外 | |

iOS 26 を最低バージョンとする理由は次の通り。

- 最新の iOS 27 と対応機種(iPhone 11 以降)が同じで、iOS 26 にしても対象から外れる機種がない。
- 最新の SwiftUI と iOS 26 からのデザインを、バージョンによる分岐なしに使える。学習中に古い API との違いを気にしなくて済む。
- 2026 年 6 月時点で、稼働中の iPhone の約 8 割が iOS 26 を使っている。一般公開する場合も対象を大きく狭めない。

## 2. 開発の段階

サーバー同期と認証は必須の機能だが、最初から抱えると学習範囲が広がりすぎるため、段階的に入れる。

| 段階 | 内容 |
|---|---|
| 第 1 段階(MVP) | iOS アプリ。データは端末内にのみ保存し、核の機能を完成させる |
| 第 2 段階 | サーバー同期と認証を追加し、端末間でデータを同期できるようにする |

Android 対応をどの段階で始めるかは未決定(7 章を参照)。

第 1 段階の時点から、同期を後付けできるデータ設計にしておく(5 章を参照)。

## 3. 機能一覧

優先度の意味: **P0** はその段階のリリースに必須、**P1** はその段階に含めるが P0 の完成後に着手する。

### 第 1 段階(MVP)

| 優先度 | 機能 | 内容 |
|---|---|---|
| P0 | 習慣の登録・編集・削除 | 習慣の名前と頻度を設定する |
| P0 | 頻度の設定 | 「毎日」と「曜日指定」(例: 月・水・金)に対応する |
| P0 | 日々のチェック | 習慣を「やった / やってない」の 2 値で記録する。1 タップで完了できること。記録のルールは後述する |
| P0 | 継続日数の表示 | 習慣ごとに、連続して達成した日数を表示する |
| P1 | リマインダー通知 | 習慣ごとに指定した時刻に、端末のローカル通知を出す |
| P1 | 統計・履歴 | 過去の記録を振り返れるようにする。具体的な表示内容は未決定 |
| P1 | ダークモード | OS の設定に追従して配色を切り替える |

### 記録と継続日数のルール

#### 日付の区切り

- 1 日の区切りは午前 4 時とする。0 時から 4 時前までの記録は前日の記録として扱う。
- 例: 水曜 1:00 にチェックした場合、火曜の記録になる。その時刻に表示する「今日」の一覧も火曜のものとする。

#### 対象日と対象外の日

- 習慣の頻度で指定した曜日を「対象日」、それ以外の曜日を「対象外の日」と呼ぶ。「毎日」の習慣では全曜日が対象日になる。
- 対象外の日にも記録を付けられる。付けた記録は履歴に残すが、継続日数には数えない。

#### 継続日数の数え方

- 継続日数は、対象日を連続して達成した回数とする。対象外の日は飛ばして数え、記録の有無にかかわらず継続を途切れさせない。
  - 例: 月・水・金の習慣で、月・水・金をすべて達成した場合、継続日数は 3 になる(暦日の 5 日ではない)。
- 今日が対象日で、まだ記録していない場合は、昨日までの継続日数を表示する。今日の区切り(翌日の午前 4 時)を過ぎても記録がなければ、継続が途切れる。
- 頻度を変更した場合、過去の日はその日に有効だった頻度で判定する。変更しても、過去の継続日数と統計は変わらない。

#### 過去の日の記録

- 過去の日の記録は、何日前でも後から付けたり外したりできる。継続日数はその結果に合わせて計算し直す。
- 記録できる範囲は、習慣を登録した日から今日までとする。登録日より前の日と未来の日には記録できない。

### 第 2 段階

| 優先度 | 機能 | 内容 |
|---|---|---|
| P0 | 認証 | SSO(Sign in with Apple、Google ログイン)とメール + パスワード |
| P0 | 端末間同期 | 同じアカウントでログインした複数の端末で、習慣と記録を同期する |

## 4. 対象外・後回しにする機能

| 機能 | 扱い | 補足 |
|---|---|---|
| ホーム画面ウィジェットなど、常に見える場所への表示 | 後回し | 入れたい機能だが MVP の後でよい |
| 数量の記録(例: 水 8 杯、読書 30 分) | 後回し | MVP は 2 値の記録のみ |
| チェック時のメモ | 後回し | |
| 「週 N 回」のような曜日を固定しない頻度 | 後回し | 継続の定義が複雑になるため |
| 英語などの多言語表示 | 後回し | 追加できる作りにはしておく(5 章) |
| 文字サイズ変更への追従、スクリーンリーダー対応 | 後回し | MVP では個別の要件にせず、OS 標準部品の挙動に任せる |
| データのエクスポート・インポート | 後回し | 第 2 段階の同期でバックアップと機種変更に対応する |
| タイムゾーンが変わったときの日付の判定 | 後回し | 海外への移動などはまれなため、MVP では考慮しない |
| Web 版 | 対象外 | |

## 5. 非機能要件

### オフライン動作

- オフライン優先とする。端末内のデータベースを正とし、通信できないときも全機能(第 2 段階の同期を除く)が使えること。
- 第 2 段階の同期は、通信できるときに裏で行う。ログインしていなくてもアプリを使い始められること。

### 同期を見据えたデータ設計

第 1 段階から次を満たす。

- レコードの識別子は、端末をまたいで衝突しない形式(UUID など)にする。
- レコードごとに更新日時を持つ。
- 削除は物理削除ではなく論理削除(削除済みの印を付ける)にする。

### 継続日数のルールに伴うデータ設計

- 記録には、午前 4 時を区切りとした日付を持たせる。チェックした時刻だけを保存して、後から日付を計算する形にはしない。
- 習慣の頻度は上書きせず、適用を始めた日付と組にした履歴として保存する。過去の日を、その日に有効だった頻度で判定するため。
- 習慣には登録日を持たせる。記録できる範囲の下限に使う。

### 対応言語

- 表示は日本語のみ。
- 文言はコードに直書きせず、文字列リソースに分ける。後から他の言語を追加できるようにするため。

### プライバシー

- 第 1 段階では、データは端末の外に出ない。
- 第 2 段階以降の取り扱い方針と、一般公開時に必要なプライバシーポリシーは未決定(7 章)。

### ライセンス

- Apache License 2.0 とする。
- 選定理由: 利用・改変・再配布を自由に認めつつ、特許の許諾と商標の扱いが明記されているため。MIT との実質的な差は小さいが、後で一般公開したときにプロジェクト名を守る根拠が増える。

## 6. 技術構成と選定理由

### 全体像

```
┌──────────────────┐   ┌──────────────────────┐
│ iOS アプリ         │   │ Android アプリ          │
│ Swift / SwiftUI   │   │ Kotlin / Jetpack Compose│
│ UI・通知           │   │ UI・通知                │
└────────┬─────────┘   └──────────┬───────────┘
         │   UniFFI が生成した呼び出しコード   │
         └──────────────┬─────────────────┘
               ┌────────┴─────────┐
               │ 共通コア (Rust)    │
               │ 習慣・継続日数の計算 │
               │ SQLite への保存    │
               │ 同期処理(第 2 段階)│
               └────────┬─────────┘
                        │ HTTPS(第 2 段階)
               ┌────────┴─────────┐      ┌──────────────┐
               │ 同期 API          │─JWT─→│ Supabase Auth │
               │ Rust (Axum)       │ 検証  │ 認証          │
               └──────────────────┘      └──────────────┘
```

### 構成要素

| 要素 | 採用 | 選定理由 |
|---|---|---|
| 共通コア | Rust | 開発者の希望。ロジックを 1 か所に置き、両 OS で挙動を揃える |
| コアの役割 | 業務ロジック、端末内 DB(SQLite)への保存、同期処理 | 保存と同期を各 OS で二重に実装すると挙動のずれが起きやすいため、コアに寄せる |
| 端末内 DB のライブラリ | rusqlite(`bundled` 機能を使う) | 端末内の SQLite に特化した同期 API で、UniFFI から呼び出しやすい。`bundled` 機能で SQLite 本体を一緒にビルドでき、iOS と Android で SQLite の版を揃えられる。SQL を直接書くため、SQL 自体も学べる |
| コアと各 OS の接続 | UniFFI | Rust の定義から Swift / Kotlin の呼び出しコードを自動生成できる。実績が多い |
| iOS の UI | Swift / SwiftUI | 開発者の希望。UI と通知は OS の流儀で書く |
| Android の UI | Kotlin / Jetpack Compose | 同上 |
| 認証(第 2 段階) | Supabase Auth | Apple、Google、メール + パスワードに対応している。パスワードの保管など危険な部分を自作しない。実務でも外部サービスに任せるのが主流 |
| 同期 API(第 2 段階) | Rust(Axum)で自作 | コアと同じ言語で書ける。Supabase Auth が発行した JWT を検証する形にし、実務でよく使う範囲の認証知識を学ぶ |

### 検討して採用しなかった案

| 案 | 採用しなかった理由 |
|---|---|
| Crux で画面の状態まで Rust に持つ | 共有範囲は最大になるが、独特の設計を追加で学ぶ必要があり、Swift / Kotlin を学ぶ機会が減る |
| Rust は計算だけにし、保存は SwiftData と Room で別々に実装する | 保存と同期の実装が二重になる |
| 認証も DB も Supabase に任せる | 最も早く動くが、サーバー側を学ぶ機会が少ない |
| 認証も含めて Rust で自作する | 仕組みは深く学べるが実務では少数派で、一般公開時に安全性の責任を負う |
| 端末内 DB に Diesel を使う | 型で検査されるクエリは安全だが、Rust を学び始めたばかりの段階では型エラーが読み解きにくい |
| 端末内 DB に SQLx を使う | 非同期処理が前提のサーバー向けの作りで、端末内 DB には重い |

### リポジトリ構成

```
habloom/
├── Cargo.toml            # Cargo workspace の定義
├── Cargo.lock
├── .cargo/config.toml    # `cargo xtask` で xtask を呼び出す別名を定義する
├── core/                 # 共通コア(crate 名は habloom-core)
├── xtask/                # ビルド手順(バインディング生成、XCFramework の作成)
├── ios/
│   ├── Habloom.xcodeproj
│   ├── Habloom/          # SwiftUI のアプリ本体
│   └── HabloomCore/      # ローカル Swift パッケージ。共通コアを Swift から使えるようにする
├── android/              # Android 対応を始めるときに追加する
├── server/               # 第 2 段階で追加する(同期 API)
└── docs/
```

#### Rust のコード

- リポジトリのルートを Cargo workspace とし、`core/` と `xtask/` をその中の crate として置く。第 2 段階の同期 API は `server/` として同じ workspace に加える。
- workspace にすると、依存ライブラリの版が `Cargo.lock` 1 つで揃い、ビルド結果の `target/` も共有できる。

#### ビルド手順

共通コアを iOS アプリから使うには、次の工程が必要になる。

1. 共通コアを、実機用(`aarch64-apple-ios`)とシミュレーター用(`aarch64-apple-ios-sim`)の静的ライブラリとしてビルドする。
2. UniFFI で、Swift から呼ぶためのコード(Swift のソースと、C の宣言であるヘッダーとモジュールマップ)を生成する。
3. 1 の 2 つのライブラリと 2 の C の宣言を、XCFramework(Apple の配布形式。Xcode がビルド先に合ったライブラリを選ぶ)にまとめる。
4. 3 と 2 の Swift のソースを `ios/HabloomCore/` に置く。

- 1〜4 は `xtask/` に Rust で書き、`cargo xtask` で実行する。
- 2〜4 の生成物は Git に含めない(`.gitignore` に入れる)。clone した後と共通コアを変更した後は、Xcode でビルドする前に `cargo xtask` を実行する。
- XCFramework は SQLite を同梱して数十 MB になる見込みで、変更のたびにコミットすると履歴が膨らむ。生成し忘れによる食い違いも防ぐ。

#### iOS アプリへの組み込み

- `ios/HabloomCore/` をローカルの Swift パッケージ(Swift Package Manager のパッケージ)とし、XCFramework と生成した Swift のソースをその中に置く。
- アプリ(`ios/Habloom/`)はこのパッケージに依存し、`import HabloomCore` で共通コアを使う。
- `Package.swift` は Git に含める。生成物とアプリのコードを分け、組み込みの設定をテキストで読める形にするため。

#### 検討して採用しなかった案

| 案 | 採用しなかった理由 |
|---|---|
| Rust のコードを `rust/` の下にまとめる | 見た目は整理されるが、cargo のコマンドを毎回 `rust/` で実行する必要があり、Rust では少数派 |
| `core/` を単独の crate にする | 最初の設定は最も少ないが、`server/` を足すときに workspace への作り替えが必要になる |
| ビルド手順をシェルスクリプトで書く | 手順は読みやすいが、Rust の練習にならない。Android 用の手順を足すときも、同じ仕組みでまとめられる xtask の方が扱いやすい |
| cargo-swift でビルドから Swift パッケージ化までを一括で行う | 中で何をしているかが見えず、つまずいたときに原因を追いにくい。Android には使えない |
| 生成物を Git に含める | Rust の環境がなくてもビルドできるが、一人で開発する間は利点が小さく、履歴が膨らむ |
| XCFramework と生成コードを Xcode プロジェクトに直接追加する | 生成物とアプリのコードが混ざる。設定が Xcode の画面操作になり、`project.pbxproj` の差分も読みにくい |

### 学習の進め方

- Rust、Swift、Kotlin はいずれも初めて学ぶ。実装では、使った言語機能とその言語らしい書き方、他の言語との違いを説明しながら進める。
- 言語間の連携(UniFFI による Rust と Swift / Kotlin の接続)と、スマホアプリの開発も初めてになる。ビルドの仕組みや用語は、初めて出たときに説明しながら進める。
- 最初の山は、Rust を iOS と Android 向けにビルドして組み込む設定(XCFramework、NDK)になる見込み。

## 7. 未決定事項

| 項目 | 決める時期の目安 | 補足 |
|---|---|---|
| 「花が咲く」の体験への活かし方 | 核の機能ができた後 | 候補: 習慣ごとに花が育つ / 庭全体が育つ / アイコンや配色のみ |

| 同期の競合解決の方式 | 第 2 段階の設計時 | 複数端末で同じ記録を変更した場合の扱い |
| 同期 API と DB のホスティング先、運用費 | 第 2 段階の設計時 | |
| ログインしていない状態で作ったデータの、ログイン後の扱い | 第 2 段階の設計時 | |
| 第 2 段階以降のデータの取り扱い方針とプライバシーポリシー | 一般公開の前 | |
| 一般公開の時期と条件 | 自分で使ってみた後 | |
